## Keys the animator placed

An animator marks moments in an animation with event keys: a footstep, a hit, the moment a coin is collected. An event key changes nothing in the picture. It is a mark on the time of the animation. The runtime tells the game when the playhead passes it.

<Diagram name="events-keys" height={240} rows={0} caption="An animation with two event keys, played twice. Each key writes a line when the playhead passes it. In the second pass the animation mixes out from 0.7 seconds." />

In the first pass both keys fire. In the second, another animation replaces this one at 0.7 seconds, and `hit` at 0.9 does not fire. An animation that mixes out fires no event, unless its `eventThreshold` allows it. The game listens for the keys instead of guessing times in code. So when the animator moves the hit, the sound moves with it.

<Snippet source={source} regions="import keys" />

The coin of Bzzz fires `onCollect` 0.23 seconds into its `collect`, and `onSound` 0.53 seconds into its `second_chance`. The bee fires `onBeeWow` 0.33 seconds into its `win`.

An event carries a name and the values the animator set: `int`, `float`, `string`, and `volume` and `balance` for an event with audio. It also carries `time`, where it sits in the animation. The listener gets the `Track` of the animation as well.

An event fires in the update in which the playhead passes it. At 60 frames a second the playhead moves about 0.017 seconds a frame, so an event fires within one frame of its time.

## The life of a track

Besides the keys of the animator, the runtime reports what happens to each animation on a track.

<Diagram name="events-life" height={200} rows={0} caption="An idle loop of one second. At 2.4 seconds a win replaces it, with a mix of 0.4 seconds. Each report appears when it happens." />

Each animation goes through these, in order:

- `start` when it starts to play.
- `complete` each time it reaches its end. A loop completes once per loop.
- `interrupt` when another animation replaces it, or `stop` with a mix fades it out, before its mix out.
- `end` when it leaves the track, after its mix out.
- `dispose` when the runtime drops it, after `end`.

`stop()` without a mix ends an animation at once, so it reports `end` with no `interrupt`. `destroy` reports nothing at all, and resolves `finished` with `'destroyed'`.

The idle above reports `complete` at 1 and 2 seconds, once per loop. At 2.4 seconds it reports `interrupt` and the win reports `start`. The idle still shows during the mix, so its `end` comes at 2.8 seconds, when the mix is over.

## Waiting for an animation

<Snippet source={source} regions="cut" />

`finished` resolves when an animation that does not loop reaches its end, or when it leaves the track for any other reason. Its value says which it was:

- `'complete'`: the animation played to its end.
- `'interrupted'`: another animation took the track.
- `'stopped'`: `stop` cleared the track or mixed it out.
- `'destroyed'`: the game destroyed the display object.

So a sequence continues only after `'complete'`, and stops when something else took control of the skeleton. The promise never rejects, so it needs no `catch`.

One case can surprise. An animation that another one replaced still plays while it mixes out. When it reaches its end in that time, `finished` resolves with `'complete'`. In every other case it resolves with `'interrupted'` when the mix out ends.

A skeleton that Pixi does not draw still moves its tracks. So `finished` resolves for a hidden skeleton too, also with `offscreen: 'pause'`.

## Cost

An update that reports nothing allocates nothing. An update that reports an event key, or a step in the life of a track, allocates a list and one small object per report. It does so also while nobody listens. The runtime then keeps no report that has no listener. It emits the reports of an update after the update, so a listener can call `play` safely.
