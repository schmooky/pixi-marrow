## An animation is a stretch of time

An animation has a length, such as 1.33 seconds. Playing it puts it on a track. The track has a playhead that moves through that length as time passes. In every frame the runtime reads the pose at the playhead and draws it, as [One frame](/how/frame/) shows. Everything that follows changes how the playhead moves.

## Know the names

An animator gives each animation a name, and a game plays them by name. Names differ between studios, so read them from the files.

<Snippet source={source} regions="import names" />

`info` lists the animations, skins, bones, slots and events of a skeleton, with the length of each animation. The command `pixi-marrow info hero.skel` prints the same as JSON.

A skeleton usually has one animation per state it can be in. The symbols of Bzzz are an example:

| Animation | What it shows | Length |
|---|---|---|
| `idle` | Rest. It loops. | 1.33 s |
| `blur_in` | Turns blurred, and stays so. | 0.27 s |
| `blur_out` | Turns sharp again. | 0.27 s |
| `landing` | A short bounce. | 0.33 s |
| `win` | A celebration. | 1.33 s |
| `disable` | A dimmed pose. | 0 s |

## Names that TypeScript checks

```bash
npx pixi-marrow typegen coin.skel --out coin.names.ts --name CoinNames
```

`typegen` writes every name of a skeleton as a TypeScript type. Run it at build time, when the animator exports the skeleton again. The command needs Node 22.12 or later.

<Snippet source={names} regions="type typed" />

Pass the type to `MarrowSpine.load`, to `MarrowSpine.from` or to `new MarrowSpine`. A name that the skeleton lacks is then a compile error in `play`, `queue`, `setMix`, `bone`, `slot`, `skin` and `skins`. Without the type, every name is a `string`, and a wrong name throws when the call runs.

<Snippet source={names} regions="events" />

The events are typed too. A listener for `event` gets the event names of the skeleton, and a wrong event name of the object does not compile.

## Loop or hold

<Diagram name="play-loop" lanes={3} timeline height={250} rows={0} caption="One animation that moves a square right in one second, played three ways. Watch what each does when the second is over." />

The first second, all of them move. Then they part:

- With `loop: true` the playhead jumps back to the start, and the move plays again.
- With `loop: false` the playhead stops at the end, and the square **holds its last frame**. It does not return to the setup pose.
- An animation of 0 seconds has only a last frame, so it is a pose that holds from the start.

<Snippet source={source} regions="loop hold" />

`play` starts an animation now, on track 0 unless you name another, in place of what the track played. Animators use 0-second animations for states that do not move, such as `disable`, which dims a Bzzz symbol and keeps it dimmed.

## Speed and part

<Diagram name="play-speed" lanes={3} timeline height={250} rows={0} caption="The same one-second move at speed 1, at speed 0.5, and with only its middle half played." />

`speed` makes the playhead move faster or slower: at 0.5 the move takes two seconds. `start` and `end` play only a part of the animation, and a loop repeats that part only. `reverse` moves the playhead backwards. `timeScale` sets the speed of the whole skeleton, every track at once.

## Stop

<Snippet source={source} regions="stop" />

`stop` removes the animation from a track, or from all tracks when you name none. Without a mix the pose stays as the track left it, because nothing changes it any more. With a mix the track fades out over that time, as an empty animation of the official runtime does. What the track keyed goes back to what the tracks below it give, or to the setup pose where they key nothing.

## Know when it ends

<Diagram name="play-finished" lanes={2} timeline height={250} rows={0} caption="A win of 1.2 seconds. On the left it plays whole. On the right another animation replaces it at 0.6 seconds." />

`play` returns a `Track`, the handle on that animation. Its `finished` promise resolves when the animation reaches its end. It also resolves when something else takes its place first, as on the right. The value of the promise says which it was:

| Value | What happened |
|---|---|
| `'complete'` | An animation that does not loop played to its end. |
| `'interrupted'` | Another animation took the track, from `play` or from the queue. |
| `'stopped'` | `stop` cleared the track or mixed it out. |
| `'destroyed'` | The game destroyed the display object. |

<Snippet source={source} regions="finished" />

The promise never rejects. An animation that loops reaches no end by itself, so its `finished` resolves when something else ends it. An animation that another one replaced resolves when its mix out ends.

## What updates the skeleton

By default a skeleton updates itself from `Ticker.shared` of Pixi, once per frame. Three options change that.

<Snippet source={life} regions="ticker" />

The `ticker` option names another ticker. With `app.ticker`, the `speed`, the `maxFPS` and `stop()` of the application reach the skeleton. `hero.ticker` reads the ticker in use.

<Snippet source={life} regions="manual" />

With `autoUpdate: false` the game calls `update` itself, with the seconds that passed. Use it for a game with its own clock, and in Node, which has no animation frames. `update` throws for seconds that are not a finite number.

The two ways differ for a skeleton that Pixi does not draw. That is a skeleton without a parent, or with `visible` or `renderable` false or an alpha of 0, on itself or on a parent. An update from the ticker places no vertex for it and draws nothing. Its tracks, its events and `finished` go on, and the render that shows it again poses it first. An `update` that you call yourself always does the whole work.

One detail matters for the cost. With one animation that plays alone on track 0, a hidden skeleton also runs no timeline. With a mix or with several tracks, the pose engine still runs the timelines, and only the vertex work stops.
